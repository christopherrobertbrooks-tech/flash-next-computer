## Pass 1 (blind)

The successful viewer demonstration reproduces, but its strongest honesty invariant does not: **the renderer can show reference state before its record is verified, and after a mismatch that unverified state remains visible**. The existing tests pass because they check the commit counter, not the full displayed state. The speed observations are useful exploratory data, with substantial caveats about teacher forcing, timing boundaries, cold compilation and cross-engine comparability.

### Findings

1. **REDLINE — the displayed machine is advanced before verification (viewer plan's central invariant is broken).**
   Spec: “The display advances only when a complete record has been checked”; after mismatch “the main panel shows the frozen last verified state.” Draft: `Shadow._next_record()` calls `self.m.record()` immediately, mutating PC/registers/RAM/digits/output before `self.expect` has matched; `V.right_pane()` and `code_window()` read `s.m` directly. `_commit()` only updates counters/highlights. `_flag()` does not restore the machine. Consequently a repaint between tokens exposes an unverified record, and a mismatch freezes the speculative reference state instead of the last verified state.

   CPU counterexample on the real reference stream: after the first token of a multi-token record, `records=0`, `verified=True`, one expected token remains, but displayed PC changes **0x41484 -> 0x41488** while last committed PC stays 0x41484. Corrupting that first token sets UNVERIFIED but leaves displayed PC at 0x41488. Smallest robust fix: maintain a separate committed display snapshot and render only that; update it atomically after the record and all its echoes match. The working checker machine can advance privately. Snapshot the whole relevant machine state (including output, PC anchor/counter, halt/fault flags), not just the existing partial before tuple. Test state equality before a partial record, after every partial token, after a wrong token and after later tokens; checking only `sh.records` cannot catch this.

2. **REDLINE — an incomplete/error termination can still finish labeled VERIFIED.**
   Spec requires budget, partial-record and end-of-answer states. Draft headless/TUI consume the worker's `('done', info)` and never finalize the shadow: no check of `in_call`, `pending`, `expect`, or an unfinished captured tool call. Worker done metadata contains only text/chip counts and seconds, without an explicit EOS/budget reason. A truncated prefix with `in_call=True`, pending record and remaining expectation reports **“VERIFIED: 2 computer tokens matched, 0 records, 1 calls”**. A model exception can similarly leave a verified-looking screen while info holds an error; headless does not return a failure exit status.

   Add `Shadow.finish(reason)` and explicit generation termination metadata. Preserve “verified prefix” if useful, but mark an unfinished frame/record **INCOMPLETE**, display runtime errors/budget termination distinctly, and never present them as a completed verified call/answer. Do not classify the normal parked machine after a completed HALT as incomplete. Add EOF fixtures after TCC, GO, a partial value record, BYTE-before-echo, HALT-before-newline, and normal EOS; add a worker-error fixture.

3. **REDLINE — queue cancellation is not cooperative when the producer is blocked.**
   Draft `on_token` checks stop once, then calls unbounded-wait `q.put(t)`. If the queue fills while playback is paused, pressing q sets stop and abandons the consumer; the producer cannot return to the stop check. The done/error handlers also use blocking `q.put`. There is no worker handle/join or cleanup `finally`. A CPU reproduction using the same check-then-put sequence shows the worker still blocked after stop is set. A daemon thread may instead be torn down when the process exits; that is not a verified orderly cancellation protocol.

   Use stop-aware timed puts for data and completion, return/manage the worker thread, set stop in a finally block, and join/confirm worker exit before treating the model as stopped. Test a full queue, quit while paused, producer error and terminal exception without loading a model. Also reset accumulated playback credit on pause: the consume condition spends existing credit even when `running=False`. The bounded FIFO preserves order in the normal single-producer path, but the model can lead playback by 4096 tokens; the entire short default example fits in that queue, so describe pause as playback pause with eventual generation backpressure, not immediate model pause.

4. **REDLINE — FLA's first full-shape timing includes cold work; the observed slowdown is not a steady-state estimate.**
   `fla_probe` warms the plain model with **64** tokens then times its first **4096**-token forward. For the circuit it times the first **4248**-token prefill after only a one-token initializer. Shape-specialized Triton compilation can occur inside those timed calls. There is one sample, no exact-shape warm-up, no alternating/repeated comparison, and unseeded random IDs for the plain prefill. Raw JSON reports 994 -> 320 text-prefill tokens/s and 2841 -> 221 circuit-prefill tokens/s with FLA, but these are first-use observations.

   Authorized GPU re-check using the same separate FLA path and circuit expression `(2**64 - 1) // 7`, resetting/injecting state each repetition: **18.9220849 s, 2.3849091 s, 2.3845920 s** for 4248 tokens (**224.5, 1781.2, 1781.4 tokens/s**), followed by `hf.check` exact on **all 4248 positions**. The cold/warm difference is ~7.9x; the warm result is ~1.6x slower than the recorded ~2841/s fallback, not ~13x. This does not establish warm plain-model performance; it was not rerun. Warm each exact shape, report cold separately, use fixed token IDs and several timed repetitions, and keep exactness checks. The probe's `chunk_kernel` detector always returns null because it looks for an attention-instance attribute that the installed implementation does not expose; dispatch uses module-level decorated functions. Availability alone is not a selected-kernel identity measurement. Inspect/profile the functions actually called and record dependency versions. Do not install or replace the live environment to perform that check.

5. **REDLINE — the round-trip gap is not an established ceiling on speeding up the real decoder.**
   Plan measurement 1 calls `timed2` “GPU time ... no CPU decode” and says its gap from a full Computer.call is the CPU round trip. Actual `timed2` is wall timing around a **Python loop** with embedding slice/expand/copy plus one graph replay per teacher-forced token; it is not GPU-event-only timing. `round_trip` also teacher-forces preloaded embeddings, reads arbitrary `x[:64]`, and does not perform code-bit extraction, `.any()`/integer conversions, mapping next-token IDs, embedding-cache lookup/stack, or feeding the predicted next token. It also leaves state altered by warm-up/capture and has no output correctness assertion. It does not measure a full `Computer.call` or RvChat loop.

   The raw incremental gap is genuinely small in this toy comparison: **4.80%, 5.34%, 4.22%** over timed2 for the three cases. Label it “incremental cost of this synthetic readback loop,” not a bound on GPU-resident decoding. Restore state around warm-up/capture; first build/check a realistic predicted-token feedback benchmark, and separately measure actual device time and end-to-end wall time. Profile the merged chat circuit too: these probes build default-target **2679-dimension standalone circuits**, without the text bridge, rather than the merged chat target (its additional capture/echo machinery and model-specific packing). Standalone `calc.elf` multiplication has **1111** trace tokens, whereas the live tool example has **2430** chip tokens; neither rate should silently stand for the other workload.

6. **NIT — teacher-forced prefill/batching are component experiments, not a completed speculative or latency optimization.**
   Probe results recalculate correctly: batch-1 **2142–2178 tokens/s**, batch-64 **21786–21830 aggregate tokens/s** (~10× throughput) while each batch step costs **6.29–6.39×** batch-1 latency. Parallel prefill is **2560/2850/2805 tokens/s**, **1.245/1.378/1.365×** its corresponding round-trip throughput. `timed2` checks an initial **up-to-300-position** prefix against the IR, not every timed position or all expressions end-to-end. `hf.check` does validate every IR dimension at all **1111/4248/14041** positions of these three provided traces; this is useful exactness evidence. But the timed prefill consumes an already known reference trace, and the stronger check is outside the timer. There is no implemented draft/verify/accept/resume protocol, free-running output check for the timed round-trip loop, or gate-suite result for a new optimization. Report these as measured component opportunities. Any retained replacement still needs the registered gate and shadow, including terminal/cache state and fallback on a rejected draft.

7. **NIT — llama-bench versus HF is a directional comparison with different workloads and precision.**
   Recomputed each llama rate directly from sample nanoseconds: **4979.25149 tokens/s at pp512**, **73.96469 at tg128** (three samples each). This is plain Qwen3.5 F16 GGUF, not Qwenputer, with F16 caches, 512-token prefill and a 128-token generation benchmark at depth 0. HF probe is BF16, a random **4096**-token prefill, and **256** greedy decode steps after a story prompt. It is valid to report both numbers, but not to call **5.01× prefill** or **1.68× decode** an isolated engine speedup or an expected integrated Qwenputer speedup. Match model tensors/precision, prompt IDs/length, cache/history depth, generated length, warm-up and repetition before a controlled claim. First establish compatibility and correctness for a merged-model port.

8. **NIT — premise conclusion needs to stay within this prompt/configuration.**
   Raw results are **0/8 off, 3/8 on**, **16 total attempts on 8 unique tasks**, one attempt per task/mode. Independently reran all **11 saved code blocks** on the reference; verdicts reproduce. The three successes are factorial, square with prologue, and Fibonacci; the sample square does include the requested save/restore sequence. The harness checks a halt/no fault/expected exit value, not all requested algorithm/ABI constraints generally. It also retains code and only a 400-character reply tail, not full generations/token counts/finish reasons. “Unreliable for unattended demos under this tested setup” is supported and a sensible reason to use verified examples. “The 4B can't write reliable RV32 assembly,” “was never trained on it,” or that phase 2 is universally impossible is not established by this small prompt test. There is no need to run new model attempts merely to adopt the safer demo design.

9. **NIT — the small screen hides critical provenance, and counters/disassembly need precise labels.**
   At **80 and 120 columns**, the single clipped source line contains neither “executor” nor the bf16 exclusion; both become visible at 200 columns. The default 120-column successful screen therefore does not meet the plan's “always visible” execution-path disclosure. Use a short persistent source line, e.g. “Reference shadow vs fp32 executor; bf16 layers NOT run,” split across lines as needed. `tokens_checked` includes forced text echoes as well as chip tokens: the reproduced demo says **2460 computer tokens** while generate reports **2430 chip tokens** (30 echoes). Call these checked stream tokens and show chip tokens separately. The plan's ~1700 “steps/s” likewise means trace tokens, not instructions/records. In `rvview.disasm`, BMAC with overwrite bit set is still displayed as `+=`; show assignment/clear-and-scale for overwrite, addition otherwise. Saved-call replay correctly discloses reconstruction and calc.elf rather than the original trace, but its claimed “as firmware would capture” extraction only drops newlines from the full parameter; it does not emulate token-window/NUL capture, so too-long/malformed calls need a limitation label or a faithful bridge replay with token provenance.

### Verification and what does work

- **Phase 1:** all **33 CPU controls** pass with saved-reply replay enabled. A deliberate in-memory disassembly mutation makes the harness exit **1**, with **8 failed controls**. It exercises real behavior rather than a permanently green path. The built-in programs, stack/ABI disassembly, refreshes, digit file and representative screen sizes work in those fixtures; no curses UI was opened.
- **Shadow baseline:** all **11 CPU controls** pass: reference-generated one/two calls, bad-token position, outside-call chip token and screen. GO, BYTE echoes, HALT newline, parking, and call capture via qwen(run=False) match the reference on successful fixtures. The mismatch latch remains false thereafter, so it does not silently realign. The full machine has nevertheless advanced at the failed record (finding 1), and EOF is unchecked (finding 2). These missing negative controls are why the current tests do not establish the advertised honesty invariant.
- **Live rerun:** default multiplication question, headless, max_new=512, default max_chip=2m, under V100 lock: exact answer **121932631112635269**; **1570 committed records**, **2430 chip tokens**, **2460 checked stream tokens**, zero mismatch, **98 text tokens**, upstream generate time **5.03925 s**. This reproduces the plan's success observation, without validating every failure/quit path. The paused-TUI and quit behavior were examined through code and CPU queue controls, not by opening or interrupting a real desktop UI.
- **Standalone circuit recheck:** default multiplication trace **1111** tokens, timed2 **464.1676 µs/step**, synthetic round trip **479.0986 µs/token**, best-of-two prefill **0.4327796 s**, hf.check exact on 1111 positions. These agree with the saved component measurements to ordinary run variation.
- **Kernel profile:** 10 graph steps after warm-up: **18 executor stages**, **36 circuit kernels per step** (8 head, 10 FFN, 18 apply), plus one DtoD input copy. Aggregate profiled device time **4690.073 µs** across ten iterations: head **2106.931**, FFN **2032.850**, apply **461.687**, copy **88.605 µs**. Profiling perturbs execution; this is not a hardware arithmetic-utilization measurement. Time inside kernels does not distinguish math from memory stalls/synchronization and does not by itself prove launch latency dominates or that fusion cannot help. The repository's original session.log has no saved kernel-profile table; this profile is review evidence.
- Deployed `rvlive.py`, `rvview.py`, `speed_probe.py` and `fla_probe.py` hashes match reviewed files. Launchers pin the V100, take its lock for phase 3, hide warnings in a log and document shell quoting. They were read but not launched interactively or edited. Review GPU runs used direct headless/probe commands and own scratch log/cache paths.

No new implementation/optimization is accepted by this review. The success cases and raw component numbers stand with the boundaries above.
