### Findings

1. **REDLINE — the displayed machine is advanced before verification (viewer plan's central invariant is broken).**
   Spec: “The display advances only when a complete record has been checked”; after mismatch “the main panel shows the frozen last verified state.” Draft: `Shadow._next_record()` calls `self.m.record()` immediately, mutating PC/registers/RAM/digits/output before `self.expect` has matched; `V.right_pane()` and `code_window()` read `s.m` directly. `_commit()` only updates counters/highlights. `_flag()` does not restore the machine. Consequently a repaint between tokens exposes an unverified record, and a mismatch freezes the speculative reference state instead of the last verified state.

   CPU counterexample on the real reference stream: after the first token of a multi-token record, `records=0`, `verified=True`, one expected token remains, but displayed PC changes **0x41484 -> 0x41488** while last committed PC stays 0x41484. Corrupting that first token sets UNVERIFIED but leaves displayed PC at 0x41488. Smallest robust fix: maintain a separate committed display snapshot and render only that; update it atomically after the record and all its echoes match. The working checker machine can advance privately. Snapshot the whole relevant machine state (including output, PC anchor/counter, halt/fault flags), not just the existing partial before tuple. Test state equality before a partial record, after every partial token, after a wrong token and after later tokens; checking only `sh.records` cannot catch this.

2. **REDLINE — an incomplete/error termination can still finish labeled VERIFIED.**
   Spec requires budget, partial-record and end-of-answer states. Draft headless/TUI consume the worker's `('done', info)` and never finalize the shadow: no check of `in_call`, `pending`, `expect`, or an unfinished captured tool call. Worker done metadata contains only text/chip counts and seconds, without an explicit EOS/budget reason. A truncated prefix with `in_call=True`, pending record and remaining expectation reports **“VERIFIED: 2 computer tokens matched, 0 records, 1 calls”**. A model exception can similarly leave a verified-looking screen while info holds an error; headless does not return a failure exit status.

   Add `Shadow.finish(reason)` and explicit generation termination metadata. Preserve “verified prefix” if useful, but mark an unfinished frame/record **INCOMPLETE**, display runtime errors/budget termination distinctly, and never present them as a completed verified call/answer. Do not classify the normal parked machine after a completed HALT as incomplete. Add EOF fixtures after TCC, GO, a partial value record, BYTE-before-echo, HALT-before-newline, and normal EOS; add a worker-error fixture.

3. **REDLINE — queue cancellation is not cooperative when the producer is blocked.**
   Draft `on_token` checks stop once, then calls unbounded-wait `q.put(t)`. If the queue fills while playback is paused, pressing q sets stop and abandons the consumer; the producer cannot return to the stop check. The done/error handlers also use blocking `q.put`. There is no worker handle/join or cleanup `finally`. A CPU reproduction using the same check-then-put sequence shows the worker still blocked after stop is set. A daemon thread may instead be torn down when the process exits; that is not a verified orderly cancellation protocol.

   Use stop-aware timed puts for data and completion, return/manage the worker thread, set stop in a finally block, and join/confirm worker exit before treating the model as stopped. Test a full queue, quit while paused, producer error and terminal exception without loading a model. Also reset accumulated playback credit on pause: the consume condition spends existing credit even when `running=False`. The bounded FIFO preserves order in the normal single-producer path, but the model can lead playback by 4096 tokens; the entire short default example fits in that queue, so describe pause as playback pause with eventual generation backpressure, not immediate model pause.

Shape-specialized Triton compilation can occur inside those timed calls. There is one sample, no exact-shape warm-up, no alternating/repeated comparison, and unseeded random IDs for the plain prefill. Raw JSON reports 994 -> 320 text-prefill tokens/s and 2841 -> 221 circuit-prefill tokens/s with FLA, but these are first-use observations.

Warm each exact shape, report cold separately, use fixed token IDs and several timed repetitions, and keep exactness checks. ### 2. The ~5% host round trip and ~20% bookkeeping estimates

The 460-to-485 µs difference is a valid observation for the specific teacher-forced readback loop. It leaves out real code-bit conversion, multiple synchronizing reads, Python token selection, embedding lookup/stack, and the feedback dependency. Both loops also contain CPU dispatch and input-copy work, so “GPU time” is the wrong description of timed2. The round-trip loop's warm-up changes recurrent state without restoring it and no correctness check protects its timed sequence.

Comparing ~2150 standalone tokens/s with **1712** in the chat chip bucket gives a roughly **20% throughput reduction**, or **26% greater seconds/token**. Neither is an isolated measurement of bookkeeping: the circuit target/bridge, kernel mix, data-dependent execution, embedding path, and timing boundaries differ. The real chat loop and computer service are not interchangeable clocks either. Keep the original ~1700 rate as an end-to-end implementation observation under its stated bucket definition. To measure the improvement ceiling, use the same circuit, firmware, trace and state in host-feedback versus device-feedback loops, restoring state and checking identical outputs; include lookup/decode operations rather than an arbitrary slice read.

### 3. Kernel profile and whether apply fusion preserves exactness

**REDLINE — naive producer/apply fusion has a cross-block ordering problem.** Both `_ffn_kernel` and `_head_kernel` use **`tl.atomic_add(y_ptr, ...)`** with potentially multiple producers of an output coordinate. `_apply_kernel` is more than addition: it waits behind the completed producer launch, reads the accumulated y, adds it to the old residual, zeros y, and after heads shifts lag history using the old input x. Producer work reads that same old x/history.

Simply accumulating into x, adding/clearing y from one producer block, or moving history updates into each head program can expose new residual/history values to other programs or consume incomplete sums. A Triton block barrier does not create a global barrier across all blocks. Even without a race, changing floating-point addition order is not automatically bit-exact. The change needs an explicit ownership/reduction scheme, immutable inputs or double buffers, correct output initialization/reset, and correct old-input history semantics. A per-output-owner kernel that computes all contributions is a possible redesign; it is not “fold 18 launches away” as a mechanically safe small edit. Test collisions, cancellation-sensitive sums, history/refresh boundaries, multiple calls, all state dimensions and complete traces before the gate/shadow.

The write-up's original profile (apply ~21%) is not saved as a raw profile artifact. My repeated standalone profile found the same **36 kernels**, but apply occupied **461.687/4690.073 = 9.84%** of aggregate device time, including the input copy in the denominator. Kernel/state/profile conditions can change costs; this is not proof that the original 21% never occurred. It does show that a fixed 20% removal gain should not be promised. Fusion also retains some necessary arithmetic/history work, so even a measured apply share is only a deletion upper bound for that component. Since chip-token work was ~12.4% of whole-question wall time in inside-4b, saving 20% of that bucket alone would save only ~2.5% of total wall time if all else stayed fixed. Batching and low utilization suggest opportunity, but do not identify pure launch latency versus memory access, atomics and sparse arithmetic. “Up to 2×” remains an engineering hypothesis.

### 4. Does emulator-draft/circuit-verify not pay, and is a custom scan required?

The experiment establishes that **one tested HF prefill implementation** supplies only a modest component speedup, not that speculative verification cannot pay on Volta. The fallback prefill already beats the corresponding synthetic round-trip throughput by **1.25–1.38×** on these cases; whether that pays after drafting, output checking, acceptance/fallback, allocation and chat-state integration has not been measured. `hf.check` copies/checks all IR dimensions against a CPU IR evaluation outside the timer; a production verifier would need a timed next-token/ownership check and valid final state, not assume that this untimed checker is free.

There is a plausible cheaper route before a full parallel scan: schedule by circuit sublayer across a known draft's positions. FFN work and q/k/v/z projections can be evaluated over positions in batches when their layer inputs are available; recurrent head updates retain sequential time dependence. A first prototype could batch the independent projections/FFNs and keep only the head recurrence sequential, possibly inside a device loop, in fp32 using the existing IR/sparse representation. Lag inputs must come from the correct earlier positions at the same sublayer. **Executor2's existing batch dimension represents independent machines; relabeling it as time is incorrect without this scheduling/state redesign.** This is a candidate to measure, not an implemented shortcut or a proven speedup. A specialized scan may ultimately help, but the current timings do not prove it is necessary. Keep rejection/fallback behavior and terminal cache state in the correctness contract.

### 5. Text speeds and the projected port gain

The **74** llama-bench rate is real for F16 plain-Qwen tg128/depth0. **44.1/48.2** are BF16 plain-Qwen story-prompt, 256-step HF loop measurements with Python argmax and cache updates. **~37/~28** are rates from different plain/widened generation paths, prompt mixes and bucket definitions, including forced response tokens and varying histories. The ~4980 prefill row should explicitly say **llama.cpp pp512**, so “the same, prompt reading” cannot be read as matched HF prefill. No measured result establishes the widened Qwenputer port's rate.

The write-up does call its port gain an estimate, which is helpful, but “would cut ...” and ranked gain “~2× end-to-end” are too definite. Conditional Amdahl arithmetic is fair: using **7620.77 s** whole-question wall and **6438.53 s** text bucket, making only that bucket **1.5×** faster saves **28.2%** total; **1.68×** saves **34.2%**; **2×** saves **42.2%**. These assume the remaining 1182.24 s and text work/counts stay fixed. ### 6. FLA fairness and the bf16 explanation

Volta's lack of native bf16 support is relevant context, **not a demonstrated cause of this measured gap**. Use exact-shape warm-ups for each mode, fixed random/prompt IDs, repetitions and cold/warm reporting. Four of five saved greedy prefixes differ; this establishes output sensitivity in the tested configurations, not the specific cause “different arithmetic order” without a controlled logits/kernel investigation. No kernel install, environment mutation or new text-model run was performed by this review.

### 7. Is llama.cpp the right next project?

It is a reasonable **portability and systems-engineering project**, especially if Chris wants it; the present numbers do not establish it as a guaranteed 2× speed win or the cheapest optimization. Recommended sequence:

- Close the viewer's committed-state, completion and cancellation issues so the verification display can serve as a trustworthy instrument.
- Build a matched plain-Qwen llama.cpp/reference baseline with the exact tool stream, budgets, prompt IDs and similar numeric/cache settings. This is a small useful milestone independent of the merged port.
- Implement the merged port in correctness milestones: explicit circuit/Qwen execution selection, separate positions/caches, firmware-state injection, circuit-owned token selection and faithful ownership/echo handling. Start unquantized; verify reference traces and final state before claiming a speed gain or experimenting with precision.
- Then measure the full system and decide between native circuit kernels, a sparse executor integration and layer-major draft verification. Keep an engine port and a circuit-kernel rewrite as independently testable changes.

A one-call demo or faster plain-model benchmark is not completion of native Qwenputer support. Conversely, a useful port need not promise better accuracy or a particular speedup to be worth sharing.
