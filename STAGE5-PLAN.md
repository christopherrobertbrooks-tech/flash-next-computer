# Stage 5 protocol: is the computer useful? (v2, 2026-10-30)

v1 (1c5e0b4) was reviewed by Muse and Codex. v2 fixes the numbers before anything runs: sample size and decision rule,
"new capability", chain design, budgets, failure layers, warm-up, a scored normal-request group, latency limits,
and a separate pilot set. Changes after the pilot are allowed; after the freeze (step 4 below), none.

## The question
On the same questions, does Flash-Next Coder get more right with the exact computer than with an ordinary Python
calculator, and what does it cost? "Alone" is also measured, as context.

## Three setups (arms)
Same Strata 0.1.41 build and model; vision off; all 12,288 experts resident (stage 4: this layout holds in every arm);
temperature 0. One fresh Strata launch per arm, with the same settings.

| Arm | Tools |
|---|---|
| **A. Alone** | none offered |
| **B. Python** | `calc` from a **persistent** host-Python MCP server (one process for the whole arm, not one per call), with the computer's input rules (stage 4 contract) |
| **C. Computer** | `calc` from the computer service (persistent process; a fresh machine session per call), every token checked against the reference machine |

**Prompts:** the same user text in every arm. The only difference is tool availability: B and C get the same tool
(same name and description, fixed for both); A gets none. Every arithmetic question ends with the stage 4 line
"End your reply with one line: ANSWER: <the exact value>."

## Budgets (per question, the same in every arm)
- `max_tokens` 8,192. Strata applies this **per generation round**, not to the whole question; every round's
  generated tokens are recorded from the engine log, and the total per question is reported.
- Tool rounds: at most **20** (`mcp.max_rounds`, raised from 8 so the longest chains fit).
- Elapsed: **600 s** per question (client timeout). Hitting any limit is a failure ("budget"), not a retry.

## Questions: 180 final + 15 pilot, generated by a fixed script
The pilot uses its own seed and is never part of the final set. The final set is generated only **after** the
generator, scorer and settings are frozen, then hashed before any final run.

| Group | Final | What it is | Scoring |
|---|---|---|---|
| 1. Exact arithmetic | 70 | multiplications, floor division, remainders, powers, gcd, fractions, decimals; 10-40 digits | exact `ANSWER:` value |
| 2. Near the computer's limits | 10 | long expressions, big powers | same (reported separately) |
| 3. Word problems, 2-5 steps | 40 | everyday-style problems needing exact big numbers | same |
| 4. Dependent chains | 40 | 8-15 steps, each needing the previous exact result ("start with 48,213; multiply by 1,237; subtract 99,991; ...") | same, plus **the first step that went wrong** (below) |
| 5a. Code with tests | 10 | small Python functions | hidden unit tests, run on Dev-Console in a `bwrap` wall (no network, read-only system, no home folder, 10 s; the gateway's AppArmor refuses bwrap) |
| 5b. Code reading | 10 | "what does this function return for input X?" | exact `ANSWER:` value (a checkable explanation question) |

Groups 1-4 (160 questions) are the **primary set**. Group 5 checks that offering a tool doesn't hurt normal work;
tool restraint (calls made on group 5) is reported separately from correctness.

**Chains:** every chain has its list of exact intermediate values. "First wrong step" = the first expected
intermediate that's missing from the tool results (B, C) or from the visible reply (A; weaker: A has no tool log).
This shows where chains break, not only whether the end was right.

**Note on the plan's predicted advantage** (exact state kept across many steps): this computer can't test it. The calc
firmware keeps no memory between calls (each call starts fresh, like the Python calculator). Group 4 therefore tests
dependent chains of separate calls, not stored state. A computer with memory needs new firmware: a separate project.

## Decision rule (primary: C vs B on the 160 primary questions)
- Measure: the paired difference in accuracy, C minus B, with a 95% confidence interval (Newcombe's method for
  paired proportions).
- **Equivalence margin: 5 points.**
  - CI entirely inside (-5, +5): **equivalent**.
  - CI entirely above 0: **computer better**. CI entirely below 0: **computer worse**.
  - Anything else: **inconclusive** (never reported as "equal").
- **Why 160:** with no true difference, the CI half-width is about 1.96 x sqrt(d / n), where d is the share of
  questions on which B and C disagree. At n = 160, equivalence is decidable for d up to ~10%. Stage 4 showed 0 of 4
  disagreements, but that's too few to rely on. If d turns out higher, the result is "inconclusive", and it's reported
  as such.
- Group breakdowns, A-vs-B and A-vs-C: **descriptive only** (counts and paired tables, no extra significance tests).

**"Practical", decided now:** C's median wall time per primary question at most **2x** B's, and at most **60 s**.
Outside that, C is "impractical" whatever its accuracy.

**"New capability", decided now:** only a pre-named task class of at least 10 questions where C gets >= 80% right and
both A and B get <= 20%. **This design contains no such class**: the computer's calculator can do nothing Python's
can't (stage 4: its five known differences are all limits). So this experiment can't produce a new-capability claim.
"Every answer is reference-checked" is a property, reported as such, not a success criterion.

## Failure layers (every failure gets exactly one, first match wins)
1. **Transport:** no reply, or HTTP error.
2. **Budget:** token, round or time limit hit (including loops: the same call repeated 3 times).
3. **Call format:** a malformed tool call, or one refused by the input rules.
4. **Backend:** the tool failed: a computer error, a reference mismatch (**must be zero**: any one stops the run),
   the computer's declared limit ("too complex"), or an out-of-memory.
5. **Final answer:** the tool results were right, but the ANSWER line is missing or wrong.
6. **Reasoning** (A, or a tool never used): the ANSWER is wrong without a tool fault.

## Timing and memory definitions
- **Warm-up:** each arm first runs 2 unscored warm-up questions. The first warm-up's time is reported as the **cold
  start**; scored timings are **steady state**.
- **Wall time:** from sending the request to receiving the full reply (non-streamed). Time to first token isn't
  measured: tool rounds run inside one non-streamed request, so it isn't a user-visible number here.
- **Tool time:** per call, from the MCP server's log (receipt to response).
- **Computer throughput:** circuit tokens / seconds inside `Computer.call`, including the reference check.
- **Memory:** V100 peak (nvidia-smi every 500 ms), host RSS of the tool process, expert residency = the engine's
  reported slot count (12,288 = all resident, so no expert cache misses are expected; any engine-reported miss
  counter is recorded if present).

## Normal-behaviour check (group 5)
B and C must each stay within **2 questions** of A on group 5 (out of 20); a bigger drop is flagged as a regression.
n = 20 is small: it's a tripwire, not a statistical test.

## Failures stay in the results
Backend failures (computer errors, out-of-memory) count as wrong answers and are listed; an arm is never restarted to
erase them. Only a **harness** bug (our scripts) allows a restart. Then the whole arm is rerun from the start and both
attempts are kept and reported.

## Stop rules
- Any computer-vs-reference mismatch: stop and investigate.
- Harness errors above 5% in an arm: stop, fix, rerun that arm from the start (both kept).
- The pilot (15 questions x 3 arms, own seed) must run cleanly before the freeze.

## Runtime (honest count)
Final 180 x 3 arms = 540, a determinism repeat of B on a fixed 40-question subset, pilot 45, warm-ups 6: **~631
requests**. At 20-40 s each: **about 3.5-7 hours** plus ~1 minute of startup per launch. One job in the V100 lock
(the 4070 and Sprocket's voice untouched); overnight.

## Order of work
1. Write the generator (pilot and final seeds), the scorer (layers, chains, sandboxed unit tests, decision rule with
   Newcombe's CI) and the runner.
2. Codex reviews them (two passes) before any GPU time.
3. Pilot (15 x 3); check in with Chris; fix what the pilot shows.
4. **Freeze:** commit the generator, scorer and settings; then generate the final 180 and record their hash.
5. Full run overnight; write-up with every failure; Codex reviews the results.

## What Chris gets
A results page with:
- the C-vs-B verdict (equivalent / better / worse / inconclusive) and its confidence interval;
- a table per group for Alone / Python / Computer;
- where chains break;
- time (cold and steady), memory, the failure list by layer;
- a plain answer on whether the computer is worth it.

All raw replies are saved.
