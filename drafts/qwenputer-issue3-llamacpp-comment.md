A follow-up on the V100: I tried running Qwenputer's language part in llama.cpp while keeping the computer exact.

**How:** the split follows `RvChat.generate`'s executor path. The computer stays on your fp32 executor for every token, and llama.cpp runs only the 32 widened Qwen layers (layers 11-42 cut out with their norm compensation, the tied embedding sliced to the 248,320 text rows), fed the same input rows `_exec_hc` builds, as llama.cpp input embeddings. Chip tokens never reach llama.cpp, and the firmware snapshot, the lock and circuit ownership are unchanged. The Qwen layers are f16; the output head can't be (it holds values up to 2^40), so it's bf16, a bit-exact copy of the checkpoint's values.

**Checks before the full run:** on 12 questions, llama.cpp picked the same next token as the HF path on 99.78% of the positions where Qwen decides, given the exact HF input rows. Plain Qwen3.5-4B scored 99.80% across the same two engines, and every disagreement was a near-tie. Along the split's own generated histories, all 23,956 rows it sent to llama.cpp were bit-identical to the rows from the checkpoint's bf16 chip-layer path (the `hf` chip path).

**Full run:** across 160 math questions, all 1,552,141 emitted chip trace tokens matched the RV32 reference. Against the HF-bf16 executor baseline on the same questions, median question latency fell from 16.77 to 10.0 seconds (1.68x), and summed time from 7,621 to 5,148 seconds (1.48x); the text steps ran at 48 vs 28 tokens/s. Accuracy was 131/160 versus 135/160; the paired 95% interval for the difference was -8.8 to +3.7 percentage points, establishing neither an accuracy difference nor equivalence. This is one run per configuration, combining engine, precision and process-split changes; the circuit itself has not been ported natively into llama.cpp. Setup as in my first post (V100, llama.cpp mainline `5e03bdd`, sm_70 build), with llama.cpp's own source unchanged.

The code, logs and full write-up are here: https://github.com/christopherrobertbrooks-tech/flash-next-computer/blob/main/results/llamacpp-port-results.md (As before, I did this with help from an AI coding assistant; every number comes from the actual runs.)
