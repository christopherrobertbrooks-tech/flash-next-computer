## Pass 1 (blind)

The saved pilot scores reproduce, but the implementation does **not** yet support the plan's claim that C and R differ only in where the CPU lives. Fix the response-stream and budget differences before drawing that causal conclusion. The viewer's CPU-first order is sensible, subject to the verification and control details below.

### Findings

1. **REDLINE — R omits a text token that C forces after every tool response.**
   Spec: INSIDE4B-PLAN says R's “response tokens are exactly the circuit's” and only CPU location differs. Draft: `inside4b/run_plain.py:50` selects text using `S.is_text(t) and o`. Upstream `Session.own[i]` describes who predicts **the next token**, not who produced token i. The final HALT echo is a newline with `own=False`, so R drops it. `response_tokens()` in B also ends one newline short. Upstream C includes that newline, then lets Qwen predict from it. The first pilot reply already shows C's `</think>\n\nANSWER` versus R/B's `</think>\nANSWER`.

   Smallest fix: R should select **all** text tokens in `toks`, without the `own` predicate. Append the HALT newline to B's forced response too. Add a CPU fixture comparing full token lists against `Session.qwen_text()` after the call, including the final newline. This is a model-input difference, not merely output whitespace; text divergence cannot be attributed wholly to wider Qwen computation before fixing it.

2. **REDLINE — the “same” computer budget has different units, scope, and a hidden third cap.**
   Spec: “at most 2,000,000 computer steps per question (C: max_chip; R: MAX_RECORDS).” Draft: upstream `RvChat.generate` counts non-text **trace tokens** cumulatively across the question; R's `Session.run(max_records=MAX_RECORDS)` counts `m.record()` calls, resetting the limit at **each tool call**. Records can emit multiple trace tokens (digit operations, value records, division). The C lock additionally calls `lock.qwen([nxt])` without passing a limit, so the reference checker has its default **1,000,000 records per call**. R's returned field called `records` actually counts non-text tokens, further confusing these units.

   Smallest fix: register one unit, preferably trace tokens, and one cumulative question limit; enforce it in both runners, and give the lock enough reference-record allowance not to introduce a stricter cap. Rename/log both instructions/records and trace tokens explicitly. Until then replace “same limits” with the actual three limits and describe this as a comparison of implementations, not an isolated CPU-location intervention. Do not silently change an in-flight frozen run; label it and version any corrected follow-up.

3. **REDLINE — B's claimed firmware-exact capture has boundary and NUL differences.**
   Spec: run_plain's docstring says it computes “exactly as Qwenputer's firmware does.” Draft `firmware_expression():61–73` only returns the too-long error for `len(call_tokens)>80`. Actual `gather()` returns -2 whenever all 80 rows are occupied without finding a terminating `<`, including **exactly 80 tokens**. Also firmware stops a token row at NUL, and stops gathering when a row begins with NUL; Python iterates embedded zero bytes and continues through later rows.

   CPU controls using synthetic tokenizer rows: `[b'<f><p>']+[b'1']*79` gives Python a 79-digit expression but firmware `error (too long: split it)`; rows `[b'<f><p>', b'1', b'\0', b'1']` give Python `1\0\x31` but firmware returns `1`. No model ran. Fix the row loop and exhaustion test to match `gather()` exactly, and retain these negative controls. B's Python evaluator also does not emulate the firmware's seven-register/stack limits, so call B an ordinary Python recipe with firmware-style framing, not an exact substitute for R/C. The pilot's B/R disagreement is consistent with a firmware complexity error absent from Python.

4. **REDLINE — distinguish the tested executor path from running the checkpoint's computer layers.**
   Spec asks about “computer in the weights,” and the viewer says phase 3 displays the CPU “as the circuit in the weights produces it.” Draft full launch uses default `--path executor`; upstream `_build_exec` builds `core.build(...)` into `Executor2`, and `_exec_step` computes that IR circuit in fp32. This path substitutes for the loaded checkpoint's computer-layer modules; it does not run those bf16 modules. `verify_mismatch` is null in all pilot C rows, so the pilot does not establish checkpoint-module/executor equivalence for these runs. Lockstep does establish agreement of the executor stream with the reference, within the completed checked prefix.

   Smallest prose fix: “C uses Qwenputer's upstream fast circuit executor, checked against the RV32 reference; this run does not execute or verify the checkpoint's bf16 computer layers.” Keep `hf` and executor/verify paths distinct in any viewer labels. Existing code's `--path hf` still uses upstream's fast HF chip view by default; do not describe it as an unrestricted full-stack slow path without checking `fast=False` and the actual launch. This narrows the interpretation; it does not make the pilot scores false.

5. **REDLINE — pilot limits must be disclosed alongside the equal-score/speed comparison.**
   The plan quotes 11/12 for all three and predicts from ~51 vs ~17 seconds. Those scores and medians are correct, but C `pilot-2-002` stops at **60,000 chip tokens**, while R/B fail `pilot-4-003` at **8,192 text tokens**. C's pilot is from an older/default chip budget, not the current two-million setting. Different stopping conditions matter to both score and latency. Proposed addition: “Pilot C used 60,000 chip tokens per question; B/R used 8,192 text tokens and R's per-call reference cap. These pilot medians are descriptive, not a matched-budget estimate of CPU placement.” The twelve paired questions give an interval about ±28.5 percentage points, so the pilot establishes neither ±5-point equivalence nor a reliable full-run speed ratio.

6. **NIT — scorer adaptation leaves R diagnostics incomplete and the delta mislabeled.**
   `stage5/score.py:262` restricts chain measures to B/C; R has no chain measures although it is now the primary comparator. The emitted key remains `C_minus_B` when `compared` is C vs R. C's `inside.chip_tokens/chip_seconds` are not read by the existing per-call measurement aggregator, so summary zeros/nulls do not mean no circuit activity. Include R in the chain conditional; use `C_minus_R` (or comparator-neutral delta), and map the runner's row-level counters explicitly. With A/B/C/R all supplied, the scorer intentionally chooses B, not R; score a C/R-only comparison when reporting inside-4b.

7. **NIT — tighten final-answer extraction and fault labels.**
   Lock errors are appended as `trace_mismatch` and cannot pass even with a correct final answer. A CPU positive/negative control confirms this. Because length is checked first, a mismatch normally appears under “budget,” while its mismatch flag remains set; preserve mismatch as the primary cause or expose both. Both runners always set `tool_calls_open=[]`, and final extraction only splits after the last response; a synthetic stopped reply containing an unanswered tool call with `ANSWER: 2` inside its parameter is accepted as a final answer. No such false pass was found in the saved pilot. Parse call/response boundaries explicitly, flag unfinished calls, and grade only assistant text outside those frames. C's regex/zip also drops unpaired calls and can misreport the firmware's actual captured expression; record capture/result events at generation boundaries instead of inferring them solely from rendered strings.

8. **NIT — viewer phase 3 must check before publishing and keep state/control semantics explicit.**
   Upstream `on_token(nxt)` fires **before** the lock verifies that token. The viewer cannot simply render state in this callback and claim every displayed state is already verified. Buffer until verification; stop visibly at mismatch and retain the last verified state. `Machine.record()` commits a whole instruction (or a refresh record); it is not one trace-token step. Buffer/check that instruction's complete token record before displaying its committed state. Show digit-file registers too: calculator arithmetic uses the custom BMAC/BMSB/BLD/BGET/BSCAN/BPRD machinery, not only x0–x31. A generic RV32IM label hides an important part of this machine.

   Phase-1 replay can truthfully rerun the recorded expression on the reference, but current saved replies contain text and counters, not original chip-token IDs, firmware/tokenizer fingerprints, or a complete original trace. Do not label that as verification/replay of the original model trace. `--calc` uses the non-bridge ELF by default whereas chat uses calc-bridge; make the distinction visible. Phase 3 needs a bounded producer/consumer buffer, pause/backpressure and cancellation semantics, and a choice between pausing generation and pausing only playback; a synchronous GPU callback plus curses loop is not a complete design. Headless tests should cover branches, loads/stores, ABI names, refreshes, custom digit ops, mismatch, EOF and terminal resize; never map a GUI or launch a model for this review.

### Independent checkpoint and prompt verification

Used `safe_open(..., device='cpu').get_slice()` in bounded **256-row** chunks, with a single CPU thread and CUDA hidden; no entire embedding/model was materialized. Checked **every element of all 426 base-language tensor blocks**, using the +11 layer mapping. **361 blocks are bit-identical; the remaining 65 are exactly the 64 layer RMS norms and final norm. All 166,400 norm elements exactly equal `bf16((1 + w_base.float()) * sqrt(2560/3968) - 1)`**, with zero mismatches, not merely matching mean ratios. Non-norm block mismatches: zero. This independently supports the base-block/norm-rescale claim and is stronger than verify_base.py's acceptance test on average ratios. It does not assert equality of the whole widened tensors, prove zero extra lanes, or establish identical finite-precision forward passes. For future regression use, strengthen verify_base.py to require elementwise rounded norm equality rather than only a near-correct mean; a mean can hide compensating errors.

Chat-template SHA256 is identical in both checkpoints: `a4aee8afcf2e0711942cf848899be66016f8d14a889ff9ede07bca099c28f715`. Tokenizer JSON/config byte hashes differ, as expected for an extended circuit vocabulary; therefore compared the actual rendered **prompt IDs for all 160 final-primary questions** with their respective tokenizers and current CALC_TOOL/settings: **160/160 identical**. The vocabularies are not universally interchangeable: seven base audio/TTS special entries are absent or moved in the extended vocabulary, outside these prompt comparisons. AutoTokenizer emitted a regex-pattern warning for the merged tokenizer; no settings were changed during this review. The exact registered question prompts match despite that warning; do not generalize this to all possible strings or modify the frozen tokenizer path without a separate versioned check.
