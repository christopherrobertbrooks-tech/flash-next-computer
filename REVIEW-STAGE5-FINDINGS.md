## Findings

1. **BLOCKER — generated code can forge a passing unit-test verdict without implementing the function.** Spec: group 5a has “hidden unit tests” and correctness means the code passes them in a wall. Draft: `score.py:run_tests` trusts the last JSON line on candidate-controlled stdout, ignores the subprocess return code, and exposes `/w/tests.json` and the runner to the submitted code. **Actual bwrap reproduction:** submitted `import json,os; print(json.dumps([True]*len(json.load(open('/w/tests.json')))),flush=True); os._exit(1)` with a test calling a nonexistent function. It returned `(True, [True])`, despite running no function/tests and exiting 1. The filesystem/network containment works for these controls; it does not make stdout a trusted verdict channel. **Smallest fix:** require successful process status and a strict result schema, and move expected outputs/verdict computation into the trusted parent. The child should receive only code/test inputs and return bounded primitive results; candidate code must not read the hidden answer file or manufacture the trusted pass list. Add both ordinary wrong-code and forged-output/early-exit controls. Confidence: high; reproduced with the actual wall, no model involved.

2. **REDLINE — the claimed Newcombe method 10 omits its positive-covariance adjustment.** Spec: “Newcombe's method for paired proportions.” Draft `score.py:newcombe_paired` uses raw `(a*d-b*c)/sqrt(marginal product)` as phi. The corrected method reduces a positive covariance numerator by `n/2`, floored at zero, before dividing. **Reproductions:** `(80,0,0,80)` returns exactly `(0,0,0)`, falsely eliminating uncertainty when every observed pair agrees; the published implementation example `(10,5,2,20)` returns limits `[-0.05484039, 0.21225124]`, versus corrected method-10 limits `[-0.06439261, 0.22111602]`. The self-test's 95% simulation at one distribution does not validate edge cases or the missing correction. **Smallest fix:** implement the corrected phi and add independent numerical fixtures, including zero discordance, boundary marginals and the 37-pair example; rerun coverage checks at multiple disagreement regimes. This is a method implementation fix, not changing the registered method after seeing outcomes. Primary implementation reference: [statsmodels method-10 source](https://www.statsmodels.org/dev/_modules/statsmodels/stats/proportion.html#confint_proportions_paired), which explicitly applies this correction and documents nonzero width for concordant pairs. Confidence: high.

3. **REDLINE — `/status` and ignored idle failures do not fence late MCP calls to their question.** Spec/runner claim: a timed-out request's late calls “never leak into the next.” Draft `ask.py` proceeds even when `wait_idle` returns None, and attaches calls by byte offsets/time of completion only. Inspected Strata sets `status['busy']=False` when each `Service.run` generation finishes; `run_with_mcp` then runs a separate worker. MCP cancellation stops the client wait and sends a cancellation notification, but this project's synchronous MCP server ignores notifications and can continue executing/logging. Thus `/status` can say idle during backend work. **CPU controls on the actual runner:** `wait_idle=None` still sent both fixture questions; after a fake first timeout, a delayed first-question call written during the second request was recorded under question 2. This is a simulated delayed transport boundary, corroborated by source lifecycle inspection, not a launched Strata trial. **Smallest fix:** fail closed when idle cannot be established, and require a real backend/request completion fence using logged begin/end IDs or equivalent acknowledged quiescence. Correlate calls with the originating request, not just completion-time slices. If quiescence cannot be proved after timeout, save that failure and stop the arm rather than issuing another question. Confidence: high.

4. **REDLINE — ordinary computer limits are treated as reference mismatches and stop the arm.** Spec: backend failures count as wrong answers; only computer/reference disagreement demands an immediate stop. Draft `ComputerBackend.run` prefixes **all** returned service errors with `computer check failed`, including record/token/time budgets; `ask.py` treats any such prefix as a reference disagreement and exits 3, and `score.py` sets `mismatch=True` on the same prefix. **CPU reproduction:** a call log containing `computer check failed: budget: more than 120 s` creates STOP and exit 3 with the message that the computer disagreed with its reference. **Smallest fix:** emit a structured error kind (`trace_mismatch`, `budget`, `reference_limit`, `execution_error`, `refused`, etc.), log it with RPC/request IDs, and stop only for the declared mismatch kinds. Keep budget/execution failures counted and attributable. Log unexpected backend exceptions too; currently the MCP catch sends an RPC error without appending a call record, so a log-only scorer can miss them. Confidence: high.

5. **REDLINE — correct final text erases budget/backend failures despite the registered failure rule.** Spec: “Hitting any limit is a failure”; backend failures count as wrong answers; each failure has a first-match layer. Draft `score_one` computes `correct` from final text/tests first and only classifies layers inside `if not ok`. A fixture with the right ANSWER and a `strata_mcp` round-limit event scores correct/no layer; the same happens with a recorded computer error and correct text. A three-identical-call loop is likewise ignored when the final answer happens to be right. Loop detection is retrospective only; the runner does not actually enforce a three-repeat stop. **Smallest fix:** compute transport/budget/tool-integrity outcomes independently of the final-answer verdict, then apply the registered whole-question eligibility and layer rule. If recovered tool faults are meant to be allowed, amend that policy explicitly before pilot/freeze. Add right-answer-plus-limit/error controls. Protocol says transport first, while the scorer special-cases HTTP OOM as backend; make that intended precedence explicit too. Confidence: high.

6. **REDLINE — chain “reached” uses the furthest matching value, not the first missing step.** Spec: “First wrong step = the first expected intermediate that's missing.” Draft `score_one` takes `max(reached)` over unordered membership. A three-step fixture with intermediates `[10,20,30]` and only result `30` reports `chain_reached=3`, and the summary calls the chain full. No earlier step was evidenced. Arm A additionally removes whitespace before digit extraction, merging adjacent numbers, and does not preserve negative signs. Repeated intermediate values can also supply multiple steps from a single occurrence. **Smallest fix:** match the longest ordered prefix with explicit occurrence handling, report the first missing step, and distinguish “unobserved/batched step” from “wrong computation.” If the scientific claim requires one call per step, request step-labelled evidence; otherwise one composed expression can legitimately skip logged intermediates. Keep final-answer accuracy separate. Confidence: high; actual scorer fixture reproduced.

7. **REDLINE — group 1's “within both tools' limits” ignores the shared capture buffer.** Generator filters numeric size only, not the tokenizer/capture contract. CPU-only audit with the actual existing Qwenputer tokenizer found the natural direct expressions for **10/70 final group-1 questions** exceed 80 captured tokens; **1/3 pilot group-1 questions** does too. For example `pilot-1-002` requires 96 tokens; final group-1 token counts include 81–102. The long-limit group also has two 88-token expressions, which is appropriate only if capture-limit refusals are part of that group. These questions are not necessarily unsolvable by decomposition, but their ordinary direct calls are refused by **both** backends, introducing a limit into the supposedly within-limit group. All these gold values still agree with exact Python. **Smallest fix:** validate canonical group-1 expressions against the actual shared contract/tokenizer, regenerating failures, and test operand/intermediate numeric bounds; explicitly label capture-limit tasks in group 2. Add a pure-data audit before freezing. Do not silently discard such cases after final results. Confidence: high.

8. **REDLINE — scorer input integrity is not enforced before paired statistics.** Draft `load_rows` overwrites earlier records with the same ID. An actual two-row fixture with duplicate `id=x` silently retained only the last row. Missing B/C primary records lead to a KeyError in `summarise` before the intended missing report is written, rather than a controlled incomplete-run artifact. Extra IDs, row arm labels, expected repeat IDs and the questions hash are not validated against a frozen manifest. **Smallest fix:** reject duplicates/mismatched arms/unknown IDs, validate the exact expected ID sets and question hash, save an explicit incomplete/error report and withhold CI/verdict until all required primary pairs exist. Validate the determinism repeat's exact 40 IDs; do not accept an arbitrary number of repeated rows as the registered subset. Confidence: high.

9. **NIT — failure diagnosis silently depends on a live mutable SSH oracle and treats unavailable as bad syntax.** `calc_says_error` asks the gateway's current Python helper while scoring. `None` on connection/import/timeout failure satisfies `is not False` and becomes `call format`. A fixture replacing only that oracle with None misclassifies a recorded backend `error` as a bad expression. This can change failure tables between identical rescoring runs. **Smallest fix:** freeze/cache the diagnostic helper/version and its outputs, classify unavailable diagnostics as unknown/harness rather than syntax, and use the same normalized input contract. Preserve underlying error strings and MCP failure events so method/format/runtime/limit errors remain distinguishable. Confidence: high.

10. **NIT — some declared measurements and code requirements are not enforced.** The runner takes tool RSS only at the end by a broad process-command match, not a named per-arm process trace; misses/round token counts are left to raw logs and per-question engine snippets are silently truncated to 20,000 characters. No code checks the requested `binary_to_int` ban on `int(b,2)`; that implementation would pass all functional tests. **Smallest fix:** state which measurements are snapshots versus peaks, persist full log offsets/paths and per-round counts, record the tool PID, and either enforce the method restriction or remove it from the scored task. Do not claim these fields are already analyzed by `score.py`. Confidence: high from source.

## 3. Is `/status` the right attribution fence?

It is useful telemetry, but **not a sufficient request/backend completion fence** in this version. Guided references near 2624 initialize `busy/queued` to false/zero; the cited code near 2716 concerns resetting busy around session save/restore. The relevant generation cleanup sets `busy=False` around line 3735. `run_with_mcp` invokes the tool worker after the model generation round returns, and uses a separate loop at 3885 onward. Thus the tool can still be executing when the generation status is idle.

`serve/mcp.py:189–207` removes the pending client wait on timeout/cancellation and sends `notifications/cancelled`; the project MCP service ignores such notifications and is synchronous. The backend can still finish and append its call log later. A next question can therefore take a new byte offset before that completion and inherit the old call. RPC IDs alone identify calls, not their originating question, unless request-to-call membership is recorded.

Additionally, `ask.py` proceeds after an idle query returns None or its 300 s limit expires. My actual-main fixture confirmed this fail-open path. Require a validated idle response **and** backend completion/acknowledged cancellation, or stop issuing requests and preserve the partial arm. A full logical-request counter spanning all MCP rounds plus pending backend calls would be a suitable signal; current engine telemetry is not. Tag begin/completion/error records with logical question IDs and persist every attempt, including timeout/parse failures, before generating the next request. These changes should be proved with a delayed-completion fixture, not only ordinary successful calls.

## 4. Is the failure classifier fair?

Shared-contract refusal is reasonably a call-format outcome when the expression violates the declared accepted-input rules. A firmware `error` versus a successful Python calculation can indicate a computer limit. But the SSH helper is not a complete syntax oracle: helper semantics differ, network/import errors are possible, and the reason the helper says `error` can itself be a numeric/resource restriction. Treating `None` as proof of bad syntax misstates the evidence. Freeze the helper/contract and cache its diagnostic output, preserve an explicit unknown category, and classify from structured backend error kinds and MCP events as well as call-log lines.

An explicit OOM should be a backend availability failure. A later 503 should also be linked to that backend incident **if** a recorded engine generation/incident ID and error metadata prove it is the same restart. A generic 503 with no such evidence stays transport/unknown; do not infer cause from order alone. Preserve raw HTTP and root-cause fields separately, and pre-register whether aggregate layers count direct transport symptoms or the evidenced root cause. Current protocol says transport first, while code overrides that for explicit OOM, so align the written hierarchy with the desired policy before freeze.

Also fix findings 4–5: a budget is not a trace mismatch, recovered errors cannot disappear simply because a final value matches, and all RPC/backend exceptions must reach the per-question record. The primary final-answer verdict and tool-integrity verdict can both be reported even when a registered whole-question failure takes precedence.

It should not be presented as uncertainty over all real-world tasks or hardware states. Shared templates and the deliberately weighted groups limit generalization.
