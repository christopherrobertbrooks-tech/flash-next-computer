# llama.cpp split-port plan review

Reviewed `llamacpp-port` **c371b29d4e243bb5563246ef631e6b7b7393e3fc**. The branch currently adds **LLAMACPP-PLAN.md only**; this is a design review, not a claim that a port runs. Compared it with deployed upstream RvChat/ExecRow source and the local llama.cpp embedding API/converter. Read-only source inspection; no GPU, model load, conversion, build, installation or implementation edit.

The split is a plausible and useful smaller target than moving the circuit into GGML. Keeping the existing checked executor avoids making circuit precision part of the initial engine port. Fix the prompt/fixture contracts before the premise test; the subsequent empirical speed and accuracy questions are well motivated.

## Findings

1. **REDLINE — prompt prefill is not covered by the proposed per-token split.**
   Goal: preserve upstream's Qwen inputs while replacing its language runtime. Plan lines 11–14 say upstream already runs every token on the executor rather than checkpoint computer layers. That is true for the executor-driven **decode steps**, but not for upstream's initial prompt path: `RvChat.generate` first calls **`self.model(input_ids=x, use_cache=True)`**, through the checkpoint stack, then snapshots the firmware and calls `_exec_start(ids)`. `ExecRow.start` processes prompt IDs from **zero circuit states/history**, then calls `load_init()` while retaining lag history. The decode `_exec_hc` recipe is therefore not by itself an explanation of how to prefill the extracted llama.cpp model.

   Add this to stage 0: “Capture the residual entering the first Qwen layer for every prompt token in the trusted HF path. Define and test how the split builds that whole prompt-row sequence, obtains first-token logits, and initializes circuit states/history before decoding. Do not substitute the raw extracted embedding table or use the parked firmware state for the prompt without a comparison proving it equivalent.” Test prompt prefill and first-token logits separately from subsequent `_exec_hc` rows, including tool syntax in the prompt. An executor-based prompt-row builder is a candidate to validate; it is not automatically established by the decode path. Narrow the introductory statement to executor-driven generation after prefill.

2. **REDLINE — the stage-0 historical fixture does not contain the exact original inputs it proposes to feed.**
   Plan lines 42–43: “feed the exact input rows HF would see for 12 saved C answers.” The saved inside-4b C replies contain rendered text and counters, **not original generated token IDs or the 23 per-position circuit keep values**. Re-encoding rendered text need not reproduce the original stream, particularly the byte-token tool responses and HALT echo. The original model/circuit state cannot simply be read from those JSON rows.

   Smallest plan fix: “Before conversion comparison, create immutable teacher-forced fixtures with explicit prompt/generated IDs, text/chip ownership, text positions, post-chip input rows, masked HF top-1 IDs and near-tie margins, plus firmware/tokenizer/code hashes. Generate both implementations' comparisons from these same fixtures.” A canonical reconstruction from saved text is legitimate as a **new** fixture, provided its tokenization and bridge handling are defined and the trusted HF inputs are captured for it; label it that way rather than calling it an exact historical replay. No free-running model answer has to be regenerated merely to create a teacher-forced test. Include prompt positions, forced response bytes and two successive calls; not just ordinary assistant words.

3. **NIT — “come for free” needs an explicit state/reset and helper contract.**
   Plan lines 17–22 claim skipped chip tokens, separate positions, firmware injection and circuit output ownership come for free; stage 2's CPU controls only specify row equality and bad-shape rejection. Reusing the executor helps preserve these behaviors, but the new helper owns independent attention/recurrent caches and positions, and its sampled token must still lose to circuit-owned **text** tokens as well as chip tokens. These are implementation obligations, not consequences of accepting an embedding matrix.

   Add acceptance controls: fresh question resets both attention and GDN/recurrent state and text position; A/B/A questions in one helper reproduce fresh A; chip-only spans do not advance Qwen; forced byte echoes and HALT newline do advance it; prefill and single-step histories agree on the same fixture; a circuit-owned token overrides helper argmax; mismatches/budgets/EOF cannot be accepted as a valid completed answer. Specify dtype/shape and framing on the pipe, explicit reset/end messages, finite input checks, helper-error/EOF propagation and child cleanup. Keep the helper under the parent's V100 lock/UUID rather than reacquiring the same lock in the child. These are small additions to the plan's tests, not a request to design every implementation detail now.

4. **NIT — make the premise stop rule reproducible before looking at its results.**
   Lines 44–45 stop when top-1 agreement is “clearly below” the plain-model control, but do not define a threshold, the 12-question selection or the comparison denominator. Choose them before testing, and compare both pairs on matched token prefixes/text positions with the same text-vocabulary mask. Report disagreements per question as well as pooled token agreement and first divergence/argmax margin; many nearly tied positions in one long answer should not silently decide the whole premise. Row/position/state correctness checks are required independently of the allowed F16-versus-BF16 top-1 disagreement. Teacher-forced agreement is a premise check, not proof that greedy full answers will remain identical; the pilot/full-run stages correctly remain necessary.

5. **NIT — two attribution claims repeat issues already corrected in the speed review.**
   Lines 24–25 say “Text is 84.5% ... this moves exactly that part.” Upstream's text bucket also includes `_exec_step` on text tokens, `_exec_hc` construction and selection/dispatch; those parts stay with the executor/host, and a pipe adds work. Replace with: “The Qwen-layer work being moved lies within the 84.5% text-step bucket; its exact share and the new boundary overhead will be measured.” The speed gain remains unknown, consistent with the plan's stated goal.

   Lines 50–51 say the plain baseline comparison “measures what f16 does to accuracy.” Comparing historical HF BF16 with llama.cpp F16 changes **both engine and precision**. Replace with “measures accuracy and latency of the combined engine/precision change.” Isolating precision would require a same-engine precision control; do not add that workload unless the question actually requires it. The same qualification applies to the planned comparison with historical C: useful port-versus-original evidence, not an isolated causal engine effect. Record clocks, timing boundaries and summed memory of all cooperating processes alongside historical comparisons.

## What is already sensible

- Extracting the **32 widened Qwen layers**, with their existing norm compensation, rather than silently substituting ordinary 2560-wide base Qwen is the appropriate split target. Keep 3968 input columns and preserve the explicit head dimensions/layer types/RoPE configuration; the existing conversion/load checks are worth doing.
- llama.cpp's local API does accept explicit float embedding rows when token IDs are absent. That supports the proposed interface in principle; it does not verify this extracted checkpoint or its numerical behavior. No runtime support is claimed by this review.
- Restricting the output head/argmax to the original text vocabulary and leaving chip ownership/execution outside llama.cpp can match the current decoder contract if the boundary tests above pass.
- A matched plain-Qwen/emulator baseline before a full split runner provides a useful result independently of the port. The immutable 160-question protocol, paired interval and explicit zero-mismatch requirement are appropriate for a later bounded system comparison.
- Keeping native circuit support optional, postponing sharing until approval, avoiding downloads initially and retaining the exact executor are proportionate choices. No new performance promises are needed.

**Outcome:** promising architecture; amend the prompt-prefill and teacher-forced fixture sections before stage 0. No implementation has been tested, and no GPU work or source-branch/main merge was performed by this review.
